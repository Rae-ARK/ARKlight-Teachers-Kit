NOAH ARKLIGHT
TEMPORARY PROJECT CONTEXT
========================================

STATUS
------
Project: Noah ARKlight
Purpose: Small side project / teaching assistant
Relationship: Companion project to ARKlight
Current intent: Take a break from compiler work while building something useful and contained.

IMPORTANT:
Noah is NOT intended to be a new compiler project.
Do not turn Noah into a large AI platform, agent framework, orchestration system,
or general-purpose educational SaaS unless explicitly requested.


1. CORE IDEA
------------

Noah is a teaching assistant designed to help a student understand concepts.

The primary loop is:

    Student asks / attempts something
            ↓
    Noah identifies the relevant concept
            ↓
    Noah explains
            ↓
    Noah provides a small example
            ↓
    Student attempts something
            ↓
    Noah evaluates the attempt
            ↓
    Noah gives feedback / hint / correction
            ↓
    Noah updates its understanding of the student's state
            ↓
    Next interaction adapts accordingly


2. DESIGN PHILOSOPHY
--------------------

Noah should teach, not merely answer questions.

Prefer:

    explanation
    → example
    → guided attempt
    → feedback
    → reinforcement

over:

    question
    → answer
    → done

The assistant should encourage the student to reason.

When appropriate, Noah should avoid immediately revealing the final answer.
It should instead provide progressively stronger hints.

Noah should distinguish between:

    - "student does not know this"
    - "student almost knows this"
    - "student made a specific misconception"
    - "student understands the concept but made a mechanical mistake"
    - "student understands the concept"

Avoid treating every incorrect answer as simply "wrong."


3. INITIAL SCOPE
----------------

Keep v0.1 extremely small.

Initial capabilities:

    - explain a concept
    - provide an example
    - ask a question
    - generate a small exercise
    - evaluate an attempt
    - provide a hint
    - summarize what was learned
    - maintain minimal student state

Do NOT initially build:

    - multi-agent systems
    - vector databases
    - complex RAG pipelines
    - autonomous agents
    - plugin ecosystems
    - elaborate analytics
    - social features
    - accounts/authentication unless actually required
    - distributed backend infrastructure
    - elaborate persistence
    - dozens of abstractions


4. EDUCATIONAL MODEL
--------------------

A concept should be representable roughly as:

    Concept
        id
        name
        description
        prerequisites
        explanations
        examples
        common_misconceptions
        exercises
        hints

Example conceptual structure:

    Concept:
        id: variables
        prerequisites: []
        explanation:
            "A variable gives a name to a stored value."
        examples:
            ...
        misconceptions:
            ...
        exercises:
            ...


5. STUDENT MODEL
----------------

Minimal student state:

    StudentState
        known_concepts
        uncertain_concepts
        failed_attempts
        misconception_hypotheses
        current_lesson

A useful conceptual representation is:

    concept → confidence

Example:

    variables       → high
    functions       → medium
    recursion       → low

This does NOT need to become a sophisticated ML model initially.

Simple deterministic state is preferable until there is a demonstrated
reason to introduce additional complexity.


6. NOAH'S BEHAVIOR
------------------

Noah should have a small set of explicit teaching actions:

    explain
    example
    question
    exercise
    hint
    evaluate
    summarize

These actions should be conceptually distinct.

For example:

    explain:
        introduce or clarify an idea

    example:
        demonstrate the idea concretely

    question:
        test conceptual understanding

    exercise:
        require the student to produce something

    hint:
        provide guidance without immediately solving

    evaluate:
        analyze the student's attempt

    summarize:
        consolidate the current understanding


7. LESSON MODEL
---------------

A lesson can initially be:

    Lesson
        concept
        introduction
        explanation
        example
        question
        exercise
        feedback
        summary

Possible interaction:

    INTRODUCTION
        ↓
    EXPLANATION
        ↓
    EXAMPLE
        ↓
    QUESTION
        ↓
    EXERCISE
        ↓
    EVALUATION
        ↓
    HINT / CORRECTION
        ↓
    SUMMARY


8. FIRST SUBJECT
----------------

Prefer starting with ONE subject rather than trying to teach everything.

Programming fundamentals are a natural candidate because they are:

    - well-defined
    - easy to exercise interactively
    - familiar territory for the project author
    - suitable for structured concept dependencies

Potential first concepts:

    values
    variables
    types
    expressions
    conditionals
    loops
    functions
    data structures
    recursion

Do not implement all of these immediately.

Start with a tiny concept set.


9. ARKLIGHT RELATIONSHIP
------------------------

Noah should USE ARKlight rather than extend the compiler unnecessarily.

Conceptual architecture:

    Noah
      │
      ├── Lesson UI
      ├── Explanation UI
      ├── Example UI
      ├── Exercise UI
      ├── Feedback UI
      └── Progress UI
             │
             ▼
          ARKlight
             │
             ▼
          Generated UI


The Noah project should therefore act as a real application built with ARKlight.

Potential future domain components:

    Lesson(...)
    Question(...)
    CodeExercise(...)
    Hint(...)
    ConceptMap(...)
    Progress(...)


These are possible future components, not requirements for v0.1.


10. IMPORTANT ARKLIGHT CONTEXT
------------------------------

ARKlight is a compiler-oriented UI/site generation framework.

Its broader architecture involves transformations such as:

    Python authoring
        ↓
    Python AST
        ↓
    ARK AST
        ↓
    normalization
        ↓
    validation
        ↓
    Website IR
        ↓
    backend
        ↓
    generated application/site

ARKlight emphasizes a central IR and multiple backends rather than having
each backend independently interpret the author's source.

Responsive design is intended to be intrinsic by default.

Interactivity is intended to operate through generated/runtime behavior
rather than requiring arbitrary user JavaScript.

ARKlight is still an evolving project.

IMPORTANT:
When Noah development requires knowledge of ARKlight's APIs or current architecture,
inspect the actual ARKlight repository/docs rather than relying on this temporary
context.

The alpha branch is specifically relevant when the user says "alpha branch."
Do not silently substitute main for alpha.


11. DEVELOPMENT PHILOSOPHY
--------------------------

Prioritize:

    correct educational behavior
        >
    simple architecture
        >
    maintainability
        >
    performance
        >
    cleverness

Do not prematurely optimize Noah.

However, implementation decisions should still be technically sound.

When discussing performance, reason from:

    data structures
    memory layout
    allocations
    control flow
    locality
    concurrency
    generated code
    I/O

Do not use "the framework will handle it" as an architectural explanation.


12. AI MODEL ROLE
-----------------

If an LLM is used, Noah should treat it as a component of the teaching system,
not as the entire architecture.

Prefer explicit application state around the model.

Conceptually:

    Student Input
        ↓
    Teaching State
        ↓
    Teaching Decision
        ↓
    Model Prompt / Call
        ↓
    Structured Result
        ↓
    Teaching State Update
        ↓
    UI


Avoid making important application state exist only inside an LLM conversation.

Where practical, model outputs should be structured and validated.


13. SAFETY / QUALITY
-------------------

Noah should:

    - avoid confidently inventing educational facts
    - distinguish uncertainty
    - explain why an answer is wrong
    - avoid humiliating the student
    - avoid excessive verbosity
    - adapt explanations when the first explanation fails
    - prefer concrete examples
    - encourage reasoning
    - avoid pretending that confidence equals correctness

For programming exercises, evaluation should distinguish:

    syntax error
    semantic error
    conceptual misunderstanding
    edge-case failure
    correct solution


14. UX PRINCIPLE
---------------

The UI should feel like a teacher's desk, not an AI dashboard.

Prefer:

    lesson
    → explanation
    → interaction
    → feedback

over:

    giant chat box
    + 18 panels
    + analytics graphs
    + AI status indicators
    + meaningless "agent" labels

The student should always know:

    What am I learning?
    What am I supposed to do?
    Why was my answer incorrect?
    What should I try next?

Very small system:

Possible logical modules:

No fixed directory structure is required yet.

16. FIRST MILESTONE
-------------------

The first meaningful milestone should be something like:

    "Noah can teach one programming concept from start to finish."

Example:

    Concept: variables

    Noah explains variables
        ↓
    shows a tiny example
        ↓
    asks a conceptual question
        ↓
    gives an exercise
        ↓
    student submits an attempt
        ↓
    Noah evaluates it
        ↓
    Noah gives a hint or correction
        ↓
    Noah summarizes the concept


If that works well, expand to another concept.

Do not expand infrastructure before this interaction is genuinely useful.


17. PROJECT SUCCESS CRITERIA
----------------------------

Noah succeeds if:

    1. A student can learn something through it.
    2. The interaction is better than simply reading an answer.
    3. Noah can recognize common mistakes.
    4. Noah can adapt its explanation.
    5. The implementation remains small enough to understand.
    6. ARKlight is actually useful for building the UI.


18. CURRENT MINDSET
-------------------

This project exists partly as a break from compiler work.

Do not turn every Noah problem into an opportunity to redesign ARKlight.

If a simple solution works, use it.

The purpose is to explore:

    educational interaction
    stateful assistance
    structured knowledge
    adaptive explanation
    practical ARKlight usage

without creating another giant systems project.

The compiler can wait.

It has survived without another abstraction for approximately five minutes.
