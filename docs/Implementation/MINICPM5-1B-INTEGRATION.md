# MiniCPM5-1B Integration

Status: **environment set up, model weights pending** — decided to
bring the GGUF file in via a `models/` directory committed/pulled into
the repo directly, rather than fighting this sandbox's network
allowlist. See "Where we got stuck" for why, and "Open questions /
next steps" for the loading code once the file lands.

## Decision, briefly

Use [MiniCPM5-1B](https://huggingface.co/openbmb/MiniCPM5-1B)
(OpenBMB, released May 2026 — after most models' training data, so
verify facts about it rather than trusting memory) as the model
behind Noah's `evaluate` and `hint` teaching actions specifically —
**not** as the source of `explain`/`example` content, which stays
Noah-authored (`Concept.explanation`/`Concept.examples` from
`Foundational/DATA-MODEL.md`). Rationale in full is in the chat
history that produced this doc; short version:

- Dense 1.08B params, Apache 2.0, runs via plain `llama.cpp`/GGUF —
  fits this project's own "small, no elaborate infra" constraint
  (`Foundational/SCOPE.md`) far better than pulling in a large model
  and a GPU-serving stack would.
- It's "1B-class SOTA," which is a narrow claim — on broader
  leaderboards it trails larger models on instruction-following and
  math specifically. That matters here because `evaluate`/`hint` need
  exactly the kind of careful distinction-drawing
  (`Foundational/TEACHING-MODEL.md`'s failure-mode taxonomy) that
  weaker instruction-following puts at risk. Scoping it away from
  `explain`/`example` limits the blast radius of that weakness: it
  never gets to author facts from scratch, only to classify/react to
  a student's attempt against Noah-supplied ground truth.

This stands in for a formal `docs/Proposals/` entry — given the
project's own "no formal review process, just written down before
built" stance, and that this was decided in-session, it's recorded
here directly rather than as a separate proposal file first.

### 2. Model runtime — done, with a detour

First attempt: `pip install transformers accelerate`. This silently
pulled the **full CUDA build of PyTorch** as a dependency of
`accelerate` (nvidia CUDA/cuDNN/NCCL wheels, `triton`, the works —
over 4GB) and ran the sandbox out of disk before `transformers` itself
finished installing. Cleaning it up:

```bash
pip uninstall -y torch triton nvidia-cublas-cu12 nvidia-cuda-cupti-cu12 \
  nvidia-cuda-nvrtc-cu12 nvidia-cuda-runtime-cu12 nvidia-cudnn-cu12 \
  nvidia-cufft-cu12 nvidia-curand-cu12 nvidia-cusolver-cu12 \
  nvidia-cusparse-cu12 nvidia-nccl-cu12 nvidia-nvjitlink-cu12 nvidia-nvtx-cu12
pip cache purge
rm -rf noah-venv/lib/python3.12/site-packages/{nvidia,cuda,torch*,sympy,networkx}
```

**Lesson for a CPU-only, small-footprint side project: don't reach for
`transformers`+`accelerate` by default.** `accelerate` assumes you
want a training-capable stack and grabs GPU wheels even when you only
want to run a 1B model for inference on CPU. This is a real,
easy-to-hit trap, not a hypothetical — it ate ~4GB and nearly the
entire disk budget for basically nothing, since MiniCPM5-1B is
explicitly designed and distributed for exactly this (CPU,
resource-constrained, on-device) scenario via a leaner path.

Second attempt, and what we're actually using:
[`llama-cpp-python`](https://github.com/abetlen/llama-cpp-python)
against MiniCPM5-1B's GGUF release. No PyTorch dependency at all —
it's a Python binding over `llama.cpp`, compiled from source
(`pyproject.toml`-based build, ~8 minutes on this sandbox's CPU, no
prebuilt wheel available for this platform). This is the right choice
for the project's actual constraints:

```bash
pip install llama-cpp-python
```

Installed clean: `llama_cpp_python 0.3.35`. `from llama_cpp import
Llama` imports fine. Total footprint after cleanup: well under 1GB,
versus the multi-GB CUDA stack the first attempt produced.

## Where we got stuck

Fetching the actual weights fails **in this specific sandbox**:

```
>>> Llama.from_pretrained(repo_id="openbmb/MiniCPM5-1B-GGUF", filename="*Q4_K_M.gguf")
FAILED: HfHubHTTPError 403 Forbidden: None.
Cannot access content at: https://huggingface.co/api/models/openbmb/MiniCPM5-1B-GGUF.
Host not in allowlist: huggingface.co. Add this host to your network egress settings to allow access.
```

Confirmed directly too — `curl -I https://huggingface.co` returns
`403` with `x-deny-reason: host_not_allowed` from this container's
egress proxy. This dev sandbox's network allowlist covers package
registries (PyPI, npm, crates, GitHub) but not model-weight hosts
(Hugging Face, ModelScope). This is an environment limitation, not
anything wrong with the plan — the runtime side (`llama-cpp-python`,
ARKlight) is fully installed and verified working; only the weight
download needs a machine with open (or specifically allowlisted)
internet.

Re-confirmed via `huggingface_hub.hf_hub_download(...)` directly
(rather than through `llama_cpp.Llama.from_pretrained`, which wraps
the same library): identical `403` at
`huggingface.co/openbmb/MiniCPM5-1B-GGUF/resolve/main/...`, no partial
file written, same `host_not_allowed` reason via a direct `curl -I` on
the resolve URL. Two different code paths, same wall — this rules out
a one-off glitch or a `Llama.from_pretrained`-specific bug; it's the
sandbox's egress policy, full stop.

## Open questions / next steps

- [ ] **Weights arriving via `models/` directory, pulled in
      separately** (not downloaded live from this environment — see
      above). Once `models/MiniCPM5-1B-Q4_K_M.gguf` (or whatever the
      actual filename turns out to be) lands, load it locally instead
      of via `Llama.from_pretrained(...)`:

      ```python
      from llama_cpp import Llama
      llm = Llama(model_path="models/MiniCPM5-1B-Q4_K_M.gguf", n_ctx=4096)
      ```

      A `.gguf` file is binary and sizable (~0.7GB at Q4_K_M) — worth
      deciding now whether it actually belongs committed to git
      (repo bloat, git isn't built for large binaries) versus
      `.gitignore`'d with a documented fetch step teammates run once
      locally. Revisit this once the file is actually here; noting it
      so it doesn't get decided by accident.
- [ ] Confirm basic generation works once loaded, and note actual
      RAM/latency numbers here.
- [ ] Design the actual `evaluate`/`hint` prompt harness — few-shot
      examples per `Foundational/TEACHING-MODEL.md`'s failure-mode
      taxonomy (syntax/semantic/conceptual/edge-case for `evaluate`;
      progressively-stronger-without-spoiling for `hint`), plus a
      structured output schema so results can be validated per
      `Foundational/DATA-MODEL.md`'s "AI model role" guidance, rather
      than trusting free-text model output directly.
- [ ] Once the harness exists, deliberately test it against the
      `variables` concept's likely misconceptions
      (`Foundational/SCOPE.md`'s first milestone) and see where a 1B
      model's weaker instruction-following actually shows up in
      practice — collapsing distinct failure modes into a generic
      "wrong," missing a specific misconception, etc. Record concrete
      failures here, not just the setup story.
- [ ] Decide whether `enable_thinking` (MiniCPM5's hybrid think/no-think
      mode) is worth turning on for `evaluate` specifically — slower,
      but plausibly helps with the graded-classification task; probably
      unnecessary for lighter actions.

## Verdict so far

As a starting point: reasonable, and the repo's own instinct ("can't
be that hard," "enough as a starting point") holds up for the parts
we could actually test — install and runtime setup for a CPU-only 1B
model genuinely is small and quick once you avoid the
`transformers`+`accelerate` GPU-stack trap. What "adapting it for this
use case" concretely requires is still ahead of us: the harness and
prompt work above, which is a real (if bounded) piece of work, not a
detail. Nothing found so far contradicts using MiniCPM5-1B for
`evaluate`/`hint` — but nothing confirms it either, since actual
inference hasn't run yet. Update the Status line at the top of this
file once it has.
